- 類似のコードが複数見つかった場合、そのコードの抽象化の是非を検討し、抽象化すべきであれば、指摘に加えてください。
  - コード全体として簡単さよりシンプルさを優先します
  - 過度な抽象化による不要な難しさは忌避しますが、既存の複数のコードを抽象化してシンプルな関数のバリエーションとして整理できるなら、その抽象化を推進します
- 類似のコードが無かったとしても、アルゴリズム・ビジネスロジックを表すインターフェースになっていない部分がある場合は、指摘してください。
  - インターフェースを適切なものに変更せず、引数の追加や、複雑化したロジックをそのままにしてしまうことは避けるべきです。
      - これは、今この瞬間のコードの変更量を小さくするため、として時折正当化されますが、避けるべきです。
  - アルゴリズム・ビジネスロジックを直接表現するインターフェースにすることは将来的な拡張性や可読性の観点からも重要です。


## UI・基盤処理の抽象化境界

UIや基盤処理についても、提供側と利用側を対応づけ、利用側へ漏れている実装知識と、共通処理に持ち込まれている利用側固有の事情を確認してください。

- 利用側が必要とする操作・役割と、実際に公開されている型・値・手順を比較する。
- 利用側が、提供側のリソース、初期化状態、接続手順などを直接扱っている場合、その知識を提供側に閉じ込められないか検討する。
- 共通処理の引数・保持状態・処理分岐に、特定のUI部品、表示更新、リソース操作など、一部の利用側だけに必要な実装知識が混在していないか確認する。
- 共通処理が担う判断・実行と、利用側固有の前後処理を区別し、専用ヘルパーやコールバックに分離することで責務と変更範囲を明確にできないか検討する。
- 重複や現在の誤用がなくても、実装詳細への結合による保守負担を評価する。

指摘では、境界を越えて共有されている実装知識、本来その知識を持つ責務、分離によって減らせる変更箇所や保守負担、追加する抽象化のコストを示してください。
低水準な型や特定用途の引数があるという理由だけでは指摘しないでください。
その実装知識が共通処理の責務に必要な場合や、分離しても同じ結合が残る場合は指摘しないでください。


## 既存の抽象化を変更する場合

共通関数・ヘルパー、基底クラス、共通インターフェースの責務・対象範囲が変わる場合、もしくはこれらが新規に追加される場合は、宣言、実装、状態の初期化、呼び出し側や派生実装を対応づけて確認してください。
公開範囲がprivateであっても、複数の操作・用途で共有される関数は対象とします。
protectedメソッドやoverride可能なプロパティも、派生実装との契約として扱います。

- 引数の型が許す値に対して、実装が要求する追加の前提条件を確認する。 特に、所有者、オブジェクト同一性、呼び出し順序への依存を調べる。
- その前提条件を呼び出し側や派生実装へ要求する必要があるか、所有者側の検索、初期化時のデータ保持、より限定された引数で不要にできないか検討する。
- 単一対象から複数対象などへ一般化する場合、引数、保持フィールド、状態、戻り値、処理分岐に旧来の前提が残っていないか確認する。
- 共通関数・ヘルパー、基底クラス、共通インターフェースに、共有対象で成立する責務が置かれ、特定の呼び出し側や派生実装だけに必要な都合が混在していないか確認する。
- 呼び出し側ごとに、使用する引数・省略する引数と、必要になる前後処理を比較し、それらの違いが共通処理の責務に属するか確認する。

現在の呼び出し側が正しく使用していることだけで、契約や責務分割の問題を指摘対象外にしないでください。
現行コードに存在する隠れた制約や不要な結合と、それを減らせる具体的な構造を示してください。


## 指摘根拠の内容

指摘の根拠として、次を可能な限り示してください。

### 共通化

- 重複または類似している具体的な箇所
- 共有している本質的な処理や不変条件
- 表面的に似ているだけではなく、同じ理由で変更されること
- 共通化によって減る不整合、修正漏れ、保守コスト
- 共通化によって不自然な条件分岐や結合が増えないこと


### アルゴリズム・ビジネスロジックを表すインターフェース

- 対象コードが表している、アルゴリズム上またはビジネス上の一まとまりの操作、判断、状態遷移
- 現在の呼び出し側に漏れ出している、実行順序、条件、特殊値、フィールドの組み合わせ、不変条件などの実装知識
- 現在の低水準な操作の組み合わせによって許されている、不完全な実行、順序違い、更新漏れ、無効な状態の生成などの具体的な不利益
- どの概念または責務を一つのインターフェースとして表現すべきか
- その処理群が、共通の事後条件、不変条件、変更理由、またはドメイン上の意味を持ち、一つの抽象化境界として妥当であること
- 抽象化によって、呼び出し側からどの知識を隠蔽し、どの誤用や保守上の負担を減らせるか

単にコードが長い、関数へ切り出せる、処理に名前を付けられる、将来再利用できる可能性があるという理由だけでは報告しないでください。
また、呼び出し側が各処理を個別に制御する必要がある場合や、抽象化しても同じ実装詳細を多数の引数として渡すだけになる場合は報告しないでください。
