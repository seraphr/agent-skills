- 類似のコードが複数見つかった場合、そのコードの抽象化の是非を検討し、抽象化すべきであれば、指摘に加えてください。
  - コード全体として簡単さよりシンプルさを優先します
  - 過度な抽象化による不要な難しさは忌避しますが、既存の複数のコードを抽象化してシンプルな関数のバリエーションとして整理できるなら、その抽象化を推進します
- 類似のコードが無かったとしても、アルゴリズム・ビジネスロジックを表すインターフェースになっていない部分がある場合は、指摘してください。
  - インターフェースを適切なものに変更せず、引数の追加や、複雑化したロジックをそのままにしてしまうことは避けるべきです。
      - これは、今この瞬間のコードの変更量を小さくするため、として時折正当化されますが、避けるべきです。
  - アルゴリズム・ビジネスロジックを直接表現するインターフェースにすることは将来的な拡張性や可読性の観点からも重要です。


## 指摘根拠の内容

指摘の根拠として、次を可能な限り示してください。

### 共通化

- 重複または類似している具体的な箇所
- 共有している本質的な処理や不変条件
- 表面的に似ているだけではなく、同じ理由で変更されること
- 共通化によって減る不整合、修正漏れ、保守コスト
- 共通化によって不自然な条件分岐や結合が増えないこと


### アルゴリズム・ビジネスロジックを表すインターフェース

- 対象コードが表している、アルゴリズム上またはビジネス上の一まとまりの操作、判断、状態遷移
- 現在の呼び出し側に漏れ出している、実行順序、条件、特殊値、フィールドの組み合わせ、不変条件などの実装知識
- 現在の低水準な操作の組み合わせによって許されている、不完全な実行、順序違い、更新漏れ、無効な状態の生成などの具体的な不利益
- どの概念または責務を一つのインターフェースとして表現すべきか
- その処理群が、共通の事後条件、不変条件、変更理由、またはドメイン上の意味を持ち、一つの抽象化境界として妥当であること
- 抽象化によって、呼び出し側からどの知識を隠蔽し、どの誤用や保守上の負担を減らせるか

単にコードが長い、関数へ切り出せる、処理に名前を付けられる、将来再利用できる可能性があるという理由だけでは報告しないでください。
また、呼び出し側が各処理を個別に制御する必要がある場合や、抽象化しても同じ実装詳細を多数の引数として渡すだけになる場合は報告しないでください。
