## 前提

このスキルでは、指定された課題を `/goal` で扱える状態にするために必要な情報を収集し、意思決定を行い、要件を決定し、方式設計・アーキテクチャ設計、を行います。
`/goal` に渡すための決定事項は、順次指定の課題にコメントとして追記していきます。

決定事項には、実装対象のユースケース、期待される振る舞い、仕様、制約、設計方針、既存実装との関係、検証方針などを含めます。
`/goal` 実行時に、エージェントが追加の大きな調査や意思決定をしなくても作業に入れる状態を目指します。

最終的に `/goal` には、以下のような短い目的だけを与える前提です。

```text
課題 ${URL} の本文及びコメントに書かれた要件・ユースケース・設計・決定事項などを全て満たす状態にしてください。
```

そのため、このスキルで追加するコメントは、単なる会話ログではなく、後続の `/goal` 実行時に参照される仕様・決定事項の一部として扱います。
コメント単体で、何を満たせばよいか、なぜその判断になったか、どの範囲が対象外か、どう検証すれば完了と見なせるかが分かるように書きます。

## 手順

1. `<skill root>/scripts/show_issue.sh`を実行して、課題の内容を確認する
    - 課題の説明、目的、背景、現在までに決まっていることを把握する
    - 特にコメントのタイトルを確認することで、すでに決まっている内容の種類を把握する
    - どのような成果物が求められているかを明確にする
    - 必要であれば関連課題や関連の既存実装なども確認して、分析に役立てる
2. `/goal` 実行時に不足しそうな決定事項の候補をいくつかユーザーに提示して選択させる
    - 具体的にユーザーから決めたい内容が指定されている場合は、選択をスキップして次に進む
    - 候補には、ユースケース、成功条件、受け入れ条件、仕様、設計方針、制約、検証方針、移行方針、対象外、許容リスクなどを含めるがこれに限らない
    - 後続の `/goal` が「Issue本文及びコメントを全て満たす」という形で実行されることを前提に、`## 決定事項の優先度`の内容を参考に、Issue上に残す価値が高い情報を優先する
3. 選択された決定事項について、ユーザーに質問し、判断をさせる 
    - 曖昧な部分がなくなるまで、必要に応じて質問を繰り返す
    - 実装判断に影響する選択肢がある場合は、ユーザーに対していきなり選択肢のみを提示せず、選択肢と共にトレードオフを明示する
4. 回答結果が、既存の決定事項と矛盾していないか・既存の決定事項に追加の情報を付与したほうが良くないかを確認する
    - 矛盾していたら、矛盾している内容をユーザーに提示して、矛盾を解消するための判断をさせる
        - この際、矛盾を解決するために過去の決定事項を変更しても良い（後からの検討で、以前の決定事項が不適切であることが判明する場合もある）
            - 変更する場合は、変更後の決定事項をユーザに提示して、変更内容を確認してもらう
            - 変更後の決定事項は、変更前の決定事項が存在しなかったかのような形で、既存コメントを編集する
                - 変更前の記述を前提としたような、「(変更前の内容)にはしない」などの記述にしてはならない
    - 既存の決定事項に追加情報を付与する場合は、追加情報をユーザに提示して、追加内容を確認してもらう
        - 例えば、すでに用語集が決定事項として存在しているが、そこに新しい用語を追加したり、既存の用語の定義をより明確にしたりする場合などが該当する
5. 結果をissueのコメント案の形にまとめてユーザーに提示し、コメントを追加して良いかどうかを質問する
    - 過去の決定事項を編集する場合は、変更後の決定事項を同時にユーザに提示する
6. ユーザーの承認を得るまで、必要に応じて情報を修正する
7. 決定事項をgithub issueのコメントに適用する
    - 過去の決定事項を変更する場合は、該当のコメントを編集する
    - 新規の決定事項は、新しいコメントとして追加する

## 決定事項の優先度

決定事項は優先度の高いものから順に、コメントとして追加していきます。
複数の優先度の決定事項を、まとめて一つのコメントで表現することもできます。

代表的な決定事項の優先順位は以下の通りですが、課題の規模・粒度により、不必要であると判断される決定事項は省略して構いませんし、必要に応じて追加することもできます。

1. ユースケース・要件・用語定義
    - その課題において、誰が、どの状況で、何を達成したいのかを明確にします
    - また、課題内や実装内で利用する用語（technical term）がある場合、その用語の定義を明確にします
        - これは、複数の決定事項の中やその後の実装で共通して利用される用語の定義を、課題内で一貫して利用するためです
    - 場合によっては課題の本文により十分な情報が記載されていることもありますが、具体的な内容が不足している場合は、ユーザーに質問して明確にします
2. 方式設計
    - ユースケース・要件を満たすために、具体的にどのような仕組み・外部システムとの連携・アルゴリズム・UIを採用するかを明確にします
3. アーキテクチャ設計
    - ユースケース・要件を満たし、方式設計を実現するための、`Architecture Definition`を明確にします
    - 実装・修正の結果構築される、抽象API・代数的構造（Computational Model）を作成し、その構造について、以下を確認します
        - その抽象APIを用いることで、ユースケース・要件を満たすことができるか
        - その抽象APIが、想定している・実際に動作している環境（物理的な構成、ネットワーク構成、プログラミング言語、フレームワーク）で実現可能か
    - 想定する将来的な拡張や変更に対して、柔軟に対応できる構造を作成します
        - あらゆる変更に対して柔軟に対応できる構造を作成することは不可能です。
        - 以下のような状態を目指すため、ユーザには今後の変更想定を確認し、それに合わせた設計を行います
            - 定義する抽象APIの構造を変更せずに対応可能
                - 課題で予定している変更
                - 直近で予定されている変更
            - 定義する抽象APIの基本的な構造を変更せず、素直な拡張（APIの単純な追加・レイヤーの追加）で対応可能
                - やることは決定していないが方向性が示されている変更
                - 将来的に想定される変更
            - 定義する抽象APIの意味合い自体を変更して対応
                - 確率が低いが、将来的に想定される変更
                - やらない方向性が示されている変更
4. 実装上の制約・制限事項
    - 設計全体には関わらないが、実装上気を付けるべきこと、やっておいてほしいごと、やってはいけないことを補助的な情報として記載します
        - 例: 既存コードの再利用方針
        - 例: 未使用になったテスト・コードの保存・削除方針
        - 例: 特定のコード（オブジェクトグラフの構築コードなど）を共通化することの指定
        - 例: オブジェクトのライフサイクル・所有権の管理方針の指定
        - 例: 具体的なライブラリの指定
        - 例: 既存の外部動作の維持・変更の可否の指定
        - 例: 個別具体的なデータ取得方法の指定


## コメント作成の観点

コメント案を作るときは、以下を必要に応じて含めます。

- ユースケース: 誰が、どの状況で、何を達成したいのか
- 受け入れ条件: 実装後に確認すべき具体的な振る舞い
- 仕様: 入出力、画面、API、状態遷移、エラー時挙動などの具体契約
- 設計方針: 既存コードのどこを使うか、どの責務に置くか、なぜその方針にするか
- 制約: 互換性、性能、権限、運用、既存データ、依存関係など
- 検証方針: 追加・更新すべきテスト、手動確認時に見るべき観点
    - その検証が本当に実現可能なのか（テストが実装可能か、手動確認がエージェントによって実施可能か）を検討し、可能なもののみを記載すること
- 対象外・未決事項・保留事項: 今回の課題では決めないこと、実装しないこと、後続課題に回すこと

特に、後続の `/goal` 実行時にエージェントが迷いやすい「対象外」「既存実装との接続」「検証方針」は優先して明文化します。
今回の課題の解決に不要な判断や、後続課題で決めるべき内容は、後続の `/goal` 実行時に勝手に確定されないように明示します。

一方であまりに細かい意思決定は、必要以上に実装を制約することになるため、記述しません。
実装中により良い方法が見つかる可能性がある場合は、あえて決定せず、後続の `/goal` 実行時にエージェントが判断できるようにします。

過度に制約が発生する典型例としては以下が挙げられますが、これに限りません。

- 具体的なモジュール構成・型名・メソッド名・変数名
    - 抽象的なレベルでモジュールの責務を決め、その説明のために具体的な構成・名前を例示する場合はありますが、その際には、あくまで例示であり実装時に抽象的な責務を満たす範囲で変更が可能であることを明示します
- 具体的なテストケース名、テストでassertする値、テストの順序
    - 抽象的なレベルでテストの観点を決め、その説明のために具体的なテストケース名やassertする値を例示する場合はありますが、その際には、あくまで例示であり実装時に抽象的な目的を満たす範囲で変更が可能であることを明示します
- 具体的な実装の手順

## コメントの書式

コメントのスケルトンは以下の通り。

```md
## ${内容を端的に表すタイトル}

タイトルは決定事項の種類を表すものとする。

- 例
    - `対象ユースケースと成功条件`
    - `受け入れ条件と対象外`
    - `API の具体契約に関する仕様`
    - `編集画面の未保存変更ポリシー`
    - `表示設定APIとイベント取得経路`
    - `既存コード再利用方針`
    - `検証方針と受け入れ条件`

### 種別

情報の種別を記述する。

- 例: ユースケース、要件、仕様、決定事項、方式設計、検証方針、制約、リスク など

#### ${内容を端的に表すタイトル1}

- 情報の具体的な内容を記述する。
- 具体的な方針・仕様に加えて、その理由や背景、選択肢の中からなぜそれを選んだのかなどの判断の根拠も含める。
- 後続の `/goal` はIssue本文とコメント全体を満たすように実行されるため、実装者がこのコメントを仕様として読める粒度で記述する。
- 曖昧な表現を避け、確認済みの前提、決定事項、対象外、未決事項・保留事項を分ける。
- 完了判定や検証方法がある場合は、箇条書きで具体的に記述する。

#### ${内容を端的に表すタイトル2}

- 1コメントが複数の決定事項で表される場合は、複数のタイトルをつけても良い。
- 個別の決定事項ごとに、理由や背景を記述する。

```

## GitHub コメント本文を安全に渡すための制約

Issue のコメントを作成・編集するとき、Markdown 本文をシェルコマンドの引数へ直接埋め込んではならない。

Markdown にはバッククォート、`$()`、引用符など、シェルが展開・実行する文字列が含まれる可能性がある。JSONエンコードやダブルクォートで囲むだけでは、シェルによるコマンド置換を防げない場合がある。

### 必須の入力方法

コメント本文は、次のいずれかの方法で `gh` コマンドへ渡す。

1. `--body-file -` を指定し、プロセスの標準入力へ本文をそのまま書き込む。
2. 標準入力を利用できない場合は、一時ファイルへ本文を文字列どおりに保存し、`--body-file <一時ファイル>` で渡す。
3. GitHub APIを使う場合も、本文をコマンドライン引数へ埋め込まず、標準入力または入力ファイルからJSONリクエストを渡す。

次のように、Markdown 本文を `--body` の引数やシェル変数展開によって渡してはならない。

```bash
# 禁止: バッククォートなどがシェルに解釈される可能性がある
gh issue comment 123 --body "<Markdown本文>"
```

本文を一時ファイルへ保存する場合は、ファイル編集に関する現在の環境の制約に従う。ヒアドキュメントや `echo` など、本文を再びシェルに解釈させる方法は使用しない。

### 編集対象の指定

既存コメントを編集するときは、事前にコメントIDまたはURLを取得し、可能な限りそのコメントを明示的に指定する。

`--edit-last` は、対象コメントが自分の最新コメントであることを直前に確認できた場合に限って使用する。調査から更新までに別のコメントが追加される可能性がある場合は、取得済みのコメントIDを使ってGitHub APIから編集する。

### 反映後の検証

コメントの作成・編集後は、必ずIssue本文とコメントをGitHubから再取得し、次を確認する。

- Markdownのバッククォート、URL、コード、改行が欠落していない。
- 承認されたコメント案と反映後の本文が一致している。
- 編集対象以外のコメントを変更していない。
- 新規コメントと既存コメントの編集を取り違えていない。

コマンド実行中に本文の一部がシェルコマンドとして実行された形跡、エラー、または欠落を検出した場合は、成功扱いにしない。対象コメントを承認済み全文で直ちに修復し、再取得して一致を確認する。

## Available scripts

スキル配下には、以下のスクリプトが用意されています。

### `<skill root>/scripts/show_issue.sh`

指定された課題の内容を表示するコマンドです。
課題の本文、コメントを全て取得して標準出力に出力します。

実行例:

```bash
<skill root>/scripts/show_issue.sh <issue_url>
```
