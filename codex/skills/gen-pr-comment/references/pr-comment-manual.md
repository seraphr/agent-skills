# レビュー指摘をPRコメントへ変換するマニュアル

## 1. 目的と適用範囲

このマニュアルは、**コメントにすることが決まっている個別のレビュー指摘**を入力として、次の二つを作るためのものです。

1. コメントを付けるファイルとソースコード範囲。
2. PRの作成者が、問題・確認事項・求められている変更を理解できるコメント本文。

入力には、コーディングエージェントによる長い説明、複数の対象箇所、修正案、再現手順などが含まれます。それらをそのまま短縮するのではなく、**このコードについて、作成者と何を確認・変更したいのかを組み立て直します。**

過去のレビュー記録や事例のGitHubページは、運用時には不要です。対象PRの差分、周辺コード、必要な仕様は、手元のファイルや提供された資料から確認できます。本書のコード例は説明用に簡略化したものであり、実際の対象コードへそのまま適用するパッチではありません。

## 2. 変換の基本方針

### 2.1. 残すのは、指摘の結論だけでなく成立条件と理由

「バグがある」「型が不適切」「共通化すべき」だけでは、作成者が判断できません。必要に応じて、次の関係を残します。

> この入力・操作・状態では、現在のコードがこう動くため、期待する結果や制約を満たせない。

ただし、明白な誤字や重複まで長く説明する必要はありません。選択範囲から理由が読み取れる場合は、一文や修正案だけで伝えられます。

### 2.2. エージェントの分類を、作成者への会話に変える

通常の本文からは、優先度、確信度スコア、発見担当、レビュー観点、受け入れ判定、無関係な検証ログを取り除きます。

代わりに、内容に合う書き出しを選びます。

- 修正内容が明確なら「〜になっています。〜にしてほしいです」。
- 挙動の意図を知りたいなら「〜になりますが、この動作は意図したものでしょうか」。
- 設計を相談したいなら「〜を常にそろえる必要があるなら、〜にまとめられないでしょうか」。
- 条件の成立が未確認なら「〜の場合、〜にならないでしょうか」。

疑問形は、問題を曖昧にするためではありません。**確認したい条件や設計上の分岐を具体的に示すため**に使います。

### 2.3. 修正案をコピーする前に、守りたい性質を取り出す

元のレビュー指摘が示した実装方法と、必要な性質は分けます。

例えば「全モデルに代入時検証を設定する」の中心は、「構築後も名前の制約が破れないこと」です。この性質を伝えれば、「再代入時に再検証する」「再代入を許さない」という選択肢を示せます。

逆に、局所的な引用漏れや誤字なら、具体的な置換をそのまま示す方が分かりやすくなります。毎回、大きな設計変更に広げる必要はありません。

元指摘にある修正案や付随するテスト要求を、すべて本文へ転記する必要もありません。例えば「Gitの参照先とビルド入力が一致しない」という広い指摘を、実行ディレクトリに依存するGit操作の説明と修正案に絞ることがあります。その場合は、本文で扱う条件と、そこで解消したい問題を明確にし、その修正で別の原因まで解消するとは書きません。

### 2.4. 指摘位置は候補であり、コメント位置は説明の焦点から決める

元指摘の先頭のファイル・行を、そのまま付与先にしません。

- 実装の不具合を、誤った期待値を固定しているテストで説明する。
- 比較処理の不具合を、比較対象となる履歴の型定義で説明する。
- 型が表せない状態の問題を、その型へ変換して保存する呼び出し箇所で説明する。
- 一方にしかない処理を、その処理が存在する側に付けて、もう一方との非対称性を問う。

このような移動を許します。付与先は、必ずしも最終的な修正先と同じではありません。

### 2.5. 追加情報は、同じ問題を理解・修正するために使う

具体的な操作例、同じ責務を持つコード、実装に必要なimport、規約に対応する設定などは補足できます。

ただし、「同じ原因から分かること」と「別の問題」は混ぜません。元指摘の説明を充実させるために、未確認の仕様、調査結果、再現経験を作らないでください。

### 2.6. 事実・推測・提案の強さをそろえる

コードで確認した事実は明確に書き、その先の未確認事項だけを留保します。

> この分岐ではプロセスの生存だけを確認しています。プロセスが生きたままAPIが応答しなくなる場合、正常と表示され続けないでしょうか。

「動作確認済み」「再現した」「すべての箇所を確認した」は、それを裏付ける記録がある場合だけ使います。元指摘での実行結果を紹介するときは「元のレビューでは、〜を確認したと報告されています」と区別します。

### 2.7. 文体は直接的で、問題に向ける

日本語のです・ます調を基本に、識別子はバッククォートで囲みます。説明の導入に長い謝辞や評価は不要です。
「○○していただけますか」のような過度に丁寧な物言いは不要です。「○○してほしいです」程度に言い換えてください。

過去のコメントには、感想、くだけた表現、エージェントへの言及もあります。汎用的な作成手順では、そこから「短く率直に言う」「理解や確認の限界を明かす」という働きを引き継ぎます。人への批判、苛立ち、確認していない個人的経験までは再現しません。

## 3. 作成に必要な入力

最低限、次の情報を用意します。

| 入力 | 用途 |
| --- | --- |
| コメント化対象の指摘本文と識別子 | 問題の中心と出力の対応を保持する |
| 対象PRの差分と、その版を識別するコミットなど | 付与先のファイル、行番号、変更前後を確定する |
| 指摘箇所と関連する周辺コード | 条件、呼び出し、データの流れを確認する |
| 関係する仕様・規約・受け入れ条件の本文 | 期待結果や要求の根拠を確定する |
| 既存スレッドの本文と位置（ある場合） | 返信として必要な補足を組み立てる |
| 再現・検証記録（ある場合） | 実測と推測を区別する |

仕様を参照する場合、URLだけではなく、関係する本文も取得します。取得できない仕様の内容を推定で埋めません。

コードや差分が不足している場合も、分かっている内容から本文案と付与候補は作れます。ただし、**行番号は推測で確定せず、付与先の未確定事項として返します。** 挙動の確認が必要なら、未確認の条件が分かる質問文にします。

## 4. 作成手順

### 手順1：指摘を六つの要素に分ける

作成用メモとして、次を抽出します。このメモをそのままPR本文へ載せる必要はありません。

| 要素 | 記述すること |
| --- | --- |
| 対象 | どの処理、値、型、説明、テストの話か |
| 条件 | どの入力・操作・環境・タイミングで成立するか |
| 現在の挙動 | コードが実際に行うこと、または元指摘が報告していること |
| 問題になる結果 | 何が失われる、誤る、区別できないのか |
| 守りたい性質 | 正しく動くために何が成立している必要があるか |
| 確認・変更したいこと | 作成者に答えてほしい点、実現してほしい状態 |

続けて、各主張を「今回コードで確認」「提供された検証記録に基づく」「元指摘のみ」「提案」に分けます。実行しなくてもコードから確定できる事実と、実行条件次第の結果を混同しません。

### 手順2：このコメントの中心を一文にする

例えば、次のように書きます。

- 「名前とIDのどちらで検索したかを、このテストデータでは区別できない」。
- 「履歴用の値が可変なので、呼び出し側が毎回コピーを忘れないことに依存している」。
- 「削除対象の型が、日付なし・時刻ありという不整合な指定を許している」。

一文にまとめにくい場合は、複数の論点が同じ根本原因・契約に属するかを確認します。

- 同じ原因の複数症状は、一つの説明の中に具体例として並べます。
- 同じ契約を複数箇所が破っているなら、代表箇所と関連箇所を示します。
- 答える内容も修正単位も異なるなら、コメント案を分けます。
- 同じコードへの二度のレビューで同じ問題が説明されている場合は、根拠を統合し、一つの説明を作ります。

一つの指摘から複数の案を作った場合も、同じ修正要求を重複させないでください。

### 手順3：何を伝えるコメントにするか決める

| 中心となる内容 | 本文の組み立て |
| --- | --- |
| 明確な不具合 | 条件 → 現在の結果 → 期待との差 → 必要な変更 |
| 意図が不明な挙動 | 現在の結果 → 意図・仕様の確認 |
| 設計上の負担 | 重複・同期・注意が必要な点 → 壊れ方 → 共通化や表現の変更 |
| テストの検証不備 | 検証したい性質 → それが壊れても通る理由 → 区別できる入力・観測結果 |
| 説明・命名の不整合 | 記述や名前 → 実際の意味との差 → 修正方向 |
| 単純な置換 | 短い説明、または置換用のsuggestion |

設計が未確定の場合、エージェントの案を唯一の正解にする必要はありません。

例えば複数フィールドの入力が原因なら、「複数フィールドを正しく扱う」か「その入力を明示的に拒否する」か、仕様上の分岐を示せます。単に「問題ありませんか」だけで終わらず、何を決める必要があるかを伝えます。

### 手順4：付与先を決める

次章の基準で、本文の中心が最も分かる位置を選びます。この時点で、関連箇所と最終的な修正先も分けて記録します。

### 手順5：本文を作り、必要な補足を付ける

最初の一、二文で何の問題かが分かるようにします。操作例や複数条件が必要なら、後ろに足します。

修正が一意でない場合は、必要な性質を明確にしたうえで、案を提案として示します。長い調査説明や参考実装は、本文の中心から分離します。

### 手順6：本文と位置を相互に点検する

選んだ範囲の横に本文だけが表示されることを想定して読みます。

- 「ここ」「この型」「このテスト」が、その範囲で特定できるか。
- 本文は、選んだ行とは別の話から始まっていないか。
- 別ファイルや反対側の分岐を問題にしている場合、その関係が本文で分かるか。
- 指摘時点と作成時点の差分が異なる場合、位置を取り直しているか。
- 本文から参照した、ソースコード上の記述が、コメント対象範囲に含まれているか。
    - 含まれていない場合は、その記述の該当行へリンクしているか。


説明の焦点が変わったら、付与先も変更します。

## 5. コメントを付ける位置と範囲

個別の指摘に直接返信できるよう、コメントは行・ファイルのレビュースレッド、または既存のレビュースレッドへの返信として作成します。
PR全体への通常コメント（Issueコメント）やレビュー本文は付与先にしません。

PR本文の記述への返信を求められた場合も、その記述を引用したうえで、話題に関連するコード行またはファイルにコメントします。
設計方針や複数箇所に共通する話は、代表するファイルへのファイルコメントにします。

適切な付与先を特定できない場合は、本文案と未確定の理由を提示します。
PR全体へのコメントで代用しません。

### 5.1. まず、何を見せながら話すかを決める

| 話したい内容 | 付与先の候補 | 選ぶ理由 |
| --- | --- | --- |
| 演算・条件分岐・例外処理の誤り | 問題の演算や分岐、例外捕捉の範囲 | 原因をその場で読める |
| 値の使い方が生む誤動作 | その値を使う処理 | 値の定義だけより影響が伝わる |
| 型が不正状態を許す | 型・フィールド・コンストラクタの定義 | 防ぐべき制約を説明できる |
| 保存・復元などの境界で情報が失われる | 不適切な型への変換・保存を選ぶ呼び出し | なぜその型を使うのが問題か分かる |
| 保証していた検証が削除された | 削除された検証の変更前側 | 失われた保証を直接示せる |
| 対になる経路の片側に処理がない | 処理がある側の呼び出し、または欠けている側の対応ブロック | 両者の差が説明しやすい |
| 間違った挙動を期待値にしている | 該当するテスト全体 | 意図と期待結果の確認がしやすい |
| テストが条件を区別できない | 操作とアサーションを含む範囲 | 壊れても通る理由が読める |
| 初期化や内部事情が利用側へ漏れている | 利用側・テスト側の特別な準備 | 利用者に負わせている負担が見える |
| 共通化すべき複数の実装 | 新しい共通定義、代表的な重複、または利用箇所 | 集約したい責務を説明しやすい |
| コメント・サンプルの説明が実装と違う | 原則として該当する説明全体。 コメントと対応するコードが近ければ対応するコードも範囲に含む | 説明が約束していることを問える |
| ファイル全体・複数の離れた箇所に関わる | ファイルコメント | 一つの行に限定された話という誤解を避ける |

「原因の行を必ず選ぶ」「修正する行にしか付けない」という固定ルールにはしません。読んだ人が、**このコメントがなぜここにあるのかを理解できること**を優先します。

### 5.2. 複数候補があるときの選び方

次の順で比較します。

1. 本文の主語となる型・処理・テストが見えるか。
2. 問題となる関係を、その範囲から読み取れるか。
3. 対象PRの差分上で位置を確実に特定できるか。
4. 同じ分かりやすさなら、無関係な処理を含まない範囲か。

同等の候補が残ったら、型の契約なら定義、動作なら利用箇所、期待結果ならテストを選びます。選択理由は作成用メモに残します。

### 5.3. 行数ではなく、意味のまとまりで範囲を選ぶ

- 一つのフィールド、呼び出し、式だけで十分なら単一行にします。
- 条件と結果、型とフィールド、操作とアサーションの関係が必要なら複数行にします。
- 小さなテストや関数の全体を選ぶ方が明確なら、その単位を選びます。
- 離れた二箇所を含めるためだけに、大きな連続範囲を選びません。一方を代表位置にして、もう一方は本文で特定します。
    - ただし、その二か所の間の距離が5行以下であれば、大きな連続範囲にしてください。
- ファイル全体への依頼は、実際のファイルコメントとして表現します。先頭行への通常コメントと混同しません。

「最大5行」などの一律の上限は設けません。短くしすぎて関係が読めなくなる場合は、必要な範囲を含めます。

#### 補足: 選択範囲だけで判定の役割が分かるようにする

コメントの選択範囲は、問題のある式を指し示すだけでなく、
その式が処理の中で果たす役割を読者が理解できる範囲にします。

- 条件分岐への指摘では、原則として条件式と、その条件で実行される
  処理を含めます。例外送出の場合は、エラーメッセージまで含めてください。
- 条件式だけを選ぶのは、分岐先の処理を読まなくても、
  指摘の理由と判定の目的が理解できる場合に限ります。
- 範囲を確定する前に、選択範囲とコメント本文だけを読むつもりで、
  「何を判定し、その結果何をするのか」が分かるか確認してください。
  分からなければ、必要な処理まで範囲を広げてください。
- 分岐全体が長い場合は、指摘に関係する結果が分かる範囲まで含めます。
  離れた処理まで大きな範囲で囲まず、関連箇所は本文からリンクしてください。

最短の範囲より、指摘を理解するために必要十分な範囲を優先します。


### 5.4. 変更前・変更後と行番号を明確にする

作成用の位置情報には、次を保持します。

- リポジトリルートからの相対ファイルパス。
- 対象差分の版。
- 変更前側か変更後側か。
- その側での開始行と終了行。行番号は1始まり、両端を含めます。
- 行コメントかファイルコメントか。
- 選択したコードの抜粋。

通常の追加・変更箇所は変更後側、削除された検証への指摘は変更前側を候補にします。変更前の行番号を変更後の行番号として扱わないでください。

既存コメントを参照するときは、投稿時の位置と現在の位置が異なる場合があります。古い行番号や現在取得できる番号だけから位置を推測せず、該当版の差分とコードを照合します。

### 5.5. 本来の対象範囲にコメントを付けられない場合

本来コメントを付けるべきコード範囲と、実際にコメントを付けられる範囲を区別します。
本来の対象範囲がPRの差分外などの理由でコメント対象にできない場合は、
次の手順で付与先と本文を決めてください。

1. 関連する変更箇所、または対象ファイルへのファイルコメントを付与先に選びます。関係の薄い変更行へ無理にコメントを付けないでください。
2. 本文では、本来の対象範囲をGitHubのソースコードへのリンクとして参照してください。リンク先は、確認したコミットSHAと行範囲を含む固定リンクにします。
3. リンクの表示名は「cleanup_storage のfstab削除処理」など、対象の役割が分かる表現にしてください。
4. 実際の付与先と本来の対象が異なるため、「ここ」「この処理」だけで対象を示さず、リンク付きの対象名を使って本文を調整してください。

ファイルコメントの場合も、指摘対象を具体的なコード範囲として特定できるなら、その範囲へのリンクを本文に含めてください。
コミットや行範囲を確認できない場合は推測でリンクを作らず、不足情報を作成用メモに記録してください。

### 5.6. 同じ問題の既存スレッドがある場合

既存スレッドへの補足なら、再現テスト、追加条件、関連箇所など、今回加える内容を中心に返信案を作ります。同じ説明を新規コメントとして繰り返しません。

返信には親コメントの識別子を保持します。位置を指定し直すための架空の行番号は作りません。

## 6. 本文の作り方

### 6.1. 通常の本文

基本形は、次の三つです。必ず三段落にするという意味ではありません。

> このコードでは〜しています。
>
> 〜の場合、〜になり、期待している〜を満たせません。
>
> 〜になるようにしてほしいです。

選択範囲だけで現状が明らかなら、条件や依頼から始められます。影響が単純なら、長い将来リスクの説明は不要です。

### 6.2. 不具合を入力・操作・状態へ翻訳する

内部の関数名を羅列するより、作成者が追える具体例を一つ示します。

- UIなら「Tabで無効なボタンへ移動し、Enterを押す」。
- 容量計算なら「空き15GB、削除予定の不完全ファイル10GB、新規作成20GB」。
- 状態管理なら「停止操作の直後、ワーカー終了前に一覧を取得する」。
- 保存形式なら「新規作成 → 未保存のままバックアップ → 復元 → 保存」。

複合条件は箇条書きにします。順序が結果を左右する場合は番号付き手順にします。実際に操作していない例は「この手順で〜になる可能性があります」など、確認状態に合う表現にします。

### 6.3. 設計の話は、人が守る必要のある条件を明らかにする

次のような依存を具体的に説明します。

- 二つの配列を常に対にして更新する必要がある。
- オブジェクトの内外にある同じIDを常に一致させる必要がある。
- 履歴へ積むたびに、複製を忘れない必要がある。
- 判定関数と抽出関数を正しい順序・組合せで呼ぶ必要がある。

そのうえで、単一の定義から導出する、型で組合せを限定する、依存を引数として渡すなど、その条件をコード側で維持する方向を提案します。

「抽象化が足りない」だけで済ませず、どの知識がどこに重複し、変更時に何がずれるのかを示してください。

### 6.4. テストへのコメントは、見逃す壊れ方を示す

「テストを追加してください」だけでなく、次の形で説明します。

> この実装の〜を削除しても、別の条件で同じ期待値になるため、テストが通ってしまいます。

よく使う説明は次の通りです。

- 名前とIDがほぼ同じなので、片方の検索が壊れても区別できない。
- Enterとblurを両方実行するので、片方が動かなくても成功する。
- 入力した値が入力欄にあることしか確認せず、確定処理の結果を見ていない。
- 検証対象とは別の条件でもボタンが無効になるため、その条件の欠落を検知できない。

必要なら、独立した入力データ、操作の分離、呼び出し結果や表示結果の検証を示します。実際に処理を削除してテストを実行していない場合は、そのような実験をしたとは書きません。

### 6.5. 命名・説明は、実際の意味との差を伝える

単に別名を提案するのではなく、現在の名前から何を誤解するのかを示します。

> この型は更新と脱退の両方に使われています。内部処理では脱退もステータス更新ですが、画面では更新と脱退を別の操作としているため、`UpdateErrors` では責務が狭く見えます。

不足している説明も具体化します。例えば配列なら、要素数、要素順、単位、座標系のうち、何が不明かを挙げます。実装から確認できない値を、推測でdocstring案に埋め込まないでください。

### 6.6. 修正案の具体性を選ぶ

| 状況 | 適した提示方法 |
| --- | --- |
| 誤字・不要な式など、変更が局所的で一意 | `suggestion`による置換 |
| 型や関数の形を見せると相談しやすい | 通常のコードブロックによる設計例 |
| 修正方法が複数ある | 必要な性質と、理由を示した具体的な変更要求。方針の選択を相談したい場合は、判断に必要な選択肢。 |
| 不具合を短い入力で示せる | 入出力例または再現テスト |
| 多段の呼び出しを追う必要がある | 条件の要約と、順序を付けた詳細説明 |

`suggestion`は、選択範囲を置換する具体案です。抜粋コードに省略記号を含めたり、別ファイルの変更まで済むように見せたりしません。

import追加など、選択範囲の外に変更が必要なら明記します。型・フォーマット・実行確認をしていない場合は、その確認を済ませたように書きません。完成した差し替えではない案は通常のコードブロックにします。

補足には、変更を実行可能にする情報も含められます。例えば、テスト名を日本語へ変える依頼に、意味が重複するdocstringの整理や、対象の規約に合わせたlint設定の変更を添える形です。いずれも、対象の設定や規約を確認してから記述します。

#### コードで表現できる例示はコードを優先する

修正案や具体例を示す場合、型・データ構造・関数シグネチャ・処理・設定・入出力など、コードで表現できるものは、自然言語だけで説明せず、コード例を優先して示してください。

- 自然言語では、問題・修正の目的・前提・判断が必要な点を説明します。
- コードの例示の前の説明では、「～を提案します」のようには表現せず、「以下のように（${簡単な説明}に）すれば、${満たしたい性質}が満たせます」のように表現してください。
    - 例: 以下のように直和型を用いれば、失敗したときのみreasonが存在し、成功時にだけresultがあることを表現できます
    - 例: 以下のような現在値と変更差分を受け取る関数を定義して利用することで、処理を共通化できます
    - 例: 以下のような割当済み・未着手タスクを利用するケースを追加し、割当済み・未着手タスクでも変更が成功がすることを確認してください
- コードでは、提案する構造や処理、具体的な値を示します。コードから読み取れる内容を自然言語で逐一言い換える必要はありません。
- 型の追加・変更を提案する場合、型名の列挙だけで済ませず、主要なフィールドと型同士の関係が分かる定義例を示してください。
- 型定義だけでは使い方や対応関係が伝わらない場合、値の構築例や利用例も必要な範囲で添えてください。
- コード例は、指摘の中心を理解するために必要十分な範囲に絞ります。関係のない実装やボイラープレートを増やさないでください。
    - 関数のシグネチャだけで説明が十分であれば、関数の本文を記述する必要はありません。
- 設計例は通常のコードブロックにし、例であることを明示します。選択範囲をそのまま置換できる修正だけを suggestion にします。
- 仕様が未確定な部分を、コード例を完成させるために推測で埋めないでください。


### 6.7. 長い根拠は、短い要点の後ろに置く

長い説明が必要な場合も、冒頭に次を置きます。

1. 何が懸念なのか。
2. どの条件や方針を確認したいのか。
3. 詳細のどこまで確認できているか。

その後に、必要なら次のような折り畳みを使います。

```html
<details>
<summary>条件と処理経路の詳細</summary>

ここに、関連する元指摘、処理経路、参考実装などを記載します。

</details>
```

元指摘を引用する場合は、引用だと分かるようにします。その場合は元の見出し等が残っても構いません。引用を載せること自体を、内容の検証済み宣言にはしません。

### 6.8. 関連箇所・規約・画像への参照

#### 共通原則

- 参照する対象と、その対象が指摘の根拠になる理由を本文に書いてください。
- 参照先は、レビューコメントの選択範囲に含めるか、本文にリンクを付けて、読者が辿れるようにしてください。本文に添付した画像・動画は、その添付自体を参照先とします。
- 引用や「直前のコメント」などの位置説明だけでは、選択範囲への包含やリンクの代わりになりません。
- リンクや添付を開かなくても、指摘の要点が本文から分かるようにしてください。
- 手元にしかない絶対パスは使わないでください。
- 参照先を特定できない場合は推測せず確認してください。確認できない場合は、不足情報として作成用メモに残してください。

#### ソースコード・コード内コメント・リポジトリ内文書

- 指摘箇所と近接し、一つの意味のまとまりになる場合は、根拠となる記述も選択範囲に含めてください。
- リンクには、確認したコミットSHAと対象の行範囲を指定してください。

#### 仕様・規約・Issue・既存の議論

- 根拠となる節やコメントへ直接リンクしてください。版を指定できる場合は、確認した版を指定してください。
- 本文には、指摘に関係する要求と、例外・許容の範囲を書いてください。
- 明文化された要求と、そこからの解釈・提案を区別してください。取得・確認できていない内容を、確定した根拠として扱わないでください。

#### 画像・動画

- 本文に添付するか、対象を直接確認できるリンクを付けてください。
- 本文には、指摘に関係する操作・条件と、画像や動画が示す結果を書いてください。
- 複数の画像や長い動画では、対象の画像・場面・時刻を特定してください。


## 7. 変換例

以下は、レビュー指摘と実際のPRコメントで確認できた変換を、名称やコードを簡略化して再構成した例です。各例の本文案は、過去コメントの逐語引用ではありません。行番号は例内だけの番号です。

### 例1：リロード漏れを、誤った期待値のテストへの質問にする

**元指摘**：ファイルの移動先しか確認していないため、`flow.yaml` を `flow.yaml.bak` へ変更してもリロードされない。移動元も処理すべき。

**関連するテスト**：

```text
41 def test_対象外拡張子への移動ではリロードしない():
42     handler.on_moved("flow.yaml", "flow.yaml.bak")
43     assert reload_calls == []
```

**付与先**：テストの41〜43行、変更後側。

**本文案**：

> 対象外の拡張子への変更は、起動時には読み込まれなくなるので、設定の削除と同じ扱いになるはずです。
> このテストではリロードしないことを正しい結果にしていますが、この期待値でよいでしょうか。

**変換の要点**：実装方法の指示から、固定している仕様の確認へ焦点を移しています。実装への指摘だから実装行に付ける、とは限りません。

### 例2：容量計算を、小さな算術例で説明する

**元指摘**：不完全イメージを後で削除するのに、事前確認では再作成サイズの全量を要求している。

**付与先**：容量確認から作成へ進む呼び出し部分、または必要容量を計算する部分。

**本文案**：

> 作成処理では不完全なイメージを削除しますが、空き容量の確認では、その削除で空く分を考慮していないようです。
>
> 空きが15GB、不完全なイメージの実割当量が10GBの状態で20GBを作り直す場合、削除後は25GB使えるので作成可能なはずです。現在の計算だと、空きが20GB未満としてエラーにならないでしょうか。

**変換の要点**：特定の計算式やコマンドの採用を先に求めず、満たしてほしい結果を共有します。

### 例3：履歴比較の不具合を、モデルの設計へ戻す

**元指摘**：スナップショットを毎回生成し、参照同一性で比較するため、内容が同じでも履歴が増える。

**コード**：

```text
18 var undoHistory: Array[MutableDocument]
19 var redoHistory: Array[MutableDocument]
```

**付与先**：履歴の型を定義する18〜19行、変更後側。

**本文案**：

> 履歴に可変な編集モデルを持たせると、保存するたびにコピーを忘れないことに依存してしまいます。この条件を呼び出し側で維持する構造は避けたいです。
>
> また、現在の比較は参照同一性によるため、内容を変更せずに編集を確定した場合でも、新しいオブジェクトが作られると履歴が追加されます。履歴には、内容で比較できる不変な値を使えないでしょうか。

**変換の要点**：比較式だけの修正から、人が注意して扱う必要のある構造へ説明を深めています。付与先も比較箇所から履歴の定義へ移します。

### 例4：独立した省略可能フィールドを、表現すべき状態の話にする

**元指摘**：日付を省略して時刻だけ指定すると、時刻が無視され全日付が削除される。検証を追加すべき。

**入力型と利用側**：

```python
class DeleteRequest:
    date: str | None
    time: str | None

# 削除処理
if request.date is None:
    delete_all_dates()
```

**付与先**：入力型の`date`と`time`を含む範囲。

**本文案**：

> この型は、日付を省略して時刻だけを指定する状態を表現できます。しかし削除処理は、日付がない場合に時刻を無視して全日付を対象にします。
>
> この組合せを作れないように、「全日付」「指定日」「指定日時」を分けた判別共用体で削除対象を表現してほしいです。

**変換の要点**：削除処理のガード追加だけでなく、入力の意味と型の整合性を要求します。削除処理の場所は本文の根拠として示します。

### 例5：型の制約を維持する方法を、選択肢として伝える

**元指摘**：名前は構築時に検証されるが、モデルへの再代入では検証されない。代入時検証を有効にすべき。

**付与先**：その名前の型を利用するモデルのフィールド行。

**本文案**：

> このモデルは名前への再代入を許していますが、その際に検証されないため、生成後に制約を満たさない名前を持たせられます。
> 再代入時に検証するか、再代入自体を許さないようにしてほしいです。

**変換の要点**：検証関数の定義ではなく、制約を維持する責任のあるモデルに付けます。同じ原因を報告した複数のレビューは、ここに統合できます。

### 例6：判定と抽出の不整合を、二方向から説明する

**元指摘**：ストリーム種別の判定と名前抽出が独立しており、不正な組合せを扱える。判別共用体を返すパーサを用意すべき。

**コード**：

```python
def is_result_stream(value: str) -> bool:
    return value.startswith("/result/")

def extract_field(value: str) -> str | None:
    # 文字列の途中にある /fields/ の後ろを抽出する
    ...
```

**付与先**：判定関数と抽出関数の関係が読める範囲。

**本文案**：

> この二つは組み合わせて使う想定に見えますが、結果ストリームではない文字列からも名前を抽出できます。逆に、結果ストリームと判定されても名前を抽出できない場合があります。
>
> 判定と抽出を一つの関数にまとめ、種別と名前を対応づけた判別共用体を返す形にできないでしょうか。

補足が必要なら、「フィールド検出は`field_name`を持つ」「パッチ検出は`patch_name`を持つ」といった型の骨格を示します。パーサの完成実装まで必須にしません。

**変換の要点**：「不正状態」という抽象語を、両関数の結果が食い違う具体的な関係へ変えます。

### 例7：テストの不足を、区別できない条件として説明する

**元指摘**：IDだけに一致する検索テストが必要。

**テストデータ**：

```python
member = {"username": "Alice", "user_id": "alice"}
query = "ali"
```

検索は大文字・小文字を区別せず、名前かIDのいずれかに一致すれば返すものとします。

**付与先**：検索条件と期待結果を示すテスト範囲。データの定義場所は本文で補足します。

**本文案**：

> テストデータの名前とIDは、大文字・小文字が違うだけになっています。検索はその違いを無視するため、ID検索が壊れていても名前検索だけでこのテストが通ってしまいます。
>
> 名前とIDに異なる文字列を使い、それぞれ片方だけに一致する条件で確認してほしいです。

**変換の要点**：追加してほしいケースの名前より、現状で何を見逃すかを先に説明します。

### 例8：暗黙の初期化を、利用側の負担から説明する

**元指摘**：ビルトイン登録が起動モジュールのimport副作用に依存し、ランタイム単体では使えない。

**付与先**：テストのfixtureで、登録目的のimportを複数並べている範囲。

**本文案**：

> 複数のテストで、ビルトインを読み込むために同じimportを並べています。利用側がこの一覧を知る必要があるのが気になります。
>
> 初期化を単一の冪等な関数にまとめ、ランタイム側から呼べないでしょうか。

**変換の要点**：起動処理の所在から、テストに漏れた内部知識へ位置を移します。初期化関数の具体案が長ければ、本文の後ろに参考コードとして添えます。

### 例9：一方の経路の処理から、反対側の欠落を問う

**元指摘**：更新時には予約領域を復元するが、新規インストール時に既存イメージを再利用すると復元されない。

**付与先**：更新経路にある`restore_reservation()`の呼び出し行。

**本文案**：

> インストール経路では、この予約領域の復元を行っていませんが大丈夫でしょうか。
> 既存イメージを再利用する判定は論理サイズだけを見ています。論理サイズは十分でも実際の割当領域が減っている場合、必要な領域を確保するという目的を満たせないように思います。

**変換の要点**：処理がない場所だけが候補ではありません。対になる処理の行に付けると、差を理解しやすい場合があります。

### 例10：削除された検証に、変更前側のコメントを付ける

**元指摘**：コンストラクタでプロセスグループの前提を検証しなくなった。

**差分**：

```diff
- if process_group_id != process.pid:
-     raise ValueError("グループのリーダーではありません")
```

**付与先**：削除された2行、変更前側。

**本文案**：

> この検証を削除したのは意図的でしょうか。
> 特定の生成関数を使うようコメントで依頼するより、この前提を満たさない値を早期にエラーにする方がよいと思います。

**変換の要点**：新しいコンストラクタの先頭より、失われた保証を直接見せます。

### 例11：型の問題を、保存操作の結果で説明する

**元指摘**：サーバー保存済みの完全なデータを表す型を、ローカルバックアップに流用している。未保存を表せず、作成日時を補うと復元後に更新扱いになる。

**付与先**：ローカル保存で`toServerOutput()`を呼んでエンコードする範囲。

**本文案**：

> この保存用の型は、未保存の状態を表せません。作成日時を現在時刻で補うと、復元後に新規作成ではなく更新として扱われます。
>
> 例えば、次の操作で作成したデータが保存時に失われる可能性があります。
>
> 1. 新規データを作り、サーバーには保存しない。
> 2. バックアップを作る。
> 3. 画面を更新し、バックアップから復元する。
> 4. サーバーへ保存する。
>
> サーバーに存在しないIDへの更新は保存されないためです。ローカル保存では、新規・保存済みの区別を保てる形式が必要です。

**変換の要点**：型定義の議論を、利用境界で起きる情報損失へつなげます。旧形式の読み込み失敗など、別の症状が同じ原因なら、段落を分けて補足できます。

### 例12：誤表示を、利用者に見えるラベルから説明する

**元指摘**：TCP接続時間とPing遅延を同じ型の判別子にまとめている。

**付与先**：`latency`の場合に「Ping」と表示する分岐。

**本文案**：

> ここでは`latency`を「Ping」と表示していますが、今回のデバイスではTCP接続の確立時間が入ります。
> Pingの結果だと誤解するので、手段に依存しない表示にするか、PingとTCPを型で区別できるようにしてほしいです。

**変換の要点**：データ構造の問題を、利用者が受け取る意味から説明します。

### 例13：小さな修正を、suggestionにする

**元指摘**：外部由来の名前をシェルコマンドへ未引用で連結している。

**付与先**：コマンドへ値を連結する行、変更後側。

**本文案**：

> 設定から受け取る値なので、シェルの一つの引数として引用しておきたいです。別途`shlex`のimportも必要です。

````markdown
```suggestion
command += f" --package {shlex.quote(name)}"
```
````

説明の誤記なら、次のようにsuggestionだけでも伝えられます。

````markdown
```suggestion
/** プロジェクトが属する組織の名前です。 */
```
````

**変換の要点**：攻撃例や一般論を繰り返す代わりに、局所的な修正を示します。選択範囲外の変更は明示します。

### 例14：広い文書修正は、代表位置と対象を分ける

**元指摘**：依存の分離後も、開発手順に「SDKと同時に型ライブラリを公開する」と残っている。

**付与先**：依存関係を変更した設定ファイルへのファイルコメント。本来の文書は差分にないものとします。

**本文案**：

> 開発手順の「SDKの公開」には、型ライブラリも同時に公開されると書かれたままです。
> 今回の分離後に同時公開される依存を確認し、開発手順の説明も合わせて更新してほしいです。

**変換の要点**：付与先と修正先が異なるため、本文で文書と節を明示します。単に「ここも直してください」とは書きません。

### 例15：環境依存の指摘を、方針の確認と根拠に分ける

**元指摘**：対応環境のうち古いOSでは、追加した設定オプションが解釈されない。

**付与先**：そのオプションを追加する処理。

**本文案**：

> 対応環境には古いOSの版も含まれていますが、元のレビューでは、その版の標準ツールはこのオプションに対応していないと報告されています。
> この環境を引き続き対象にするなら、そこで動く方法が必要です。対応対象を変更する方針であれば、環境の説明も合わせる必要があります。
>
> バージョンごとの実動作は未確認なので、以下に元指摘の根拠を添えます。

この後に、提供されたバージョン情報と処理経路を折り畳みで載せます。

**変換の要点**：複雑な対策の実装を即座に指定せず、対象環境という前提を明らかにします。元指摘の根拠と今回の確認範囲を分けます。

## 8. 半自動作成の出力形式

エージェントは、**PRに載せる本文**と、**人が内容・位置を確認するためのメモ**を分けて返します。以下は作成用の内部形式であり、GitHub APIへそのまま渡す形式ではありません。

```yaml
comments:
  - source_finding_ids:
      - "指摘-001"
    target:
      kind: "line" # line / file / reply
      revision: "対象差分の版を特定するコミット等"
      path: "src/example.py"
      side: "new" # old / new。変更前側・変更後側
      start_line: 41
      end_line: 43
      parent_comment_id: null
      code_excerpt: |
        選択したコードをそのまま記載
    body: |
      ここにPRへ載せるコメント本文だけを記載します。
    authoring_notes:
      central_point: "このコメントで確認・変更したいこと"
      location_reason: "なぜこの範囲が説明に適しているか"
      related_locations:
        - path: "src/related.py"
          symbol_or_section: "関連する関数・型・節"
          role: "原因・利用側・対になる経路・実際の修正先など"
      evidence:
        - claim: "本文に含めた主張"
          basis: "今回コードで確認／提供された検証記録／元指摘のみ／提案"
          detail: "確認した箇所と、分かること"
      additions_to_source:
        - "元指摘に補足した内容と、その根拠"
      unresolved:
        - "位置や表現の確定に不足している情報。なければ空配列"
      location_status: "resolved" # resolved / needs_context
```

形式ごとの規則は次の通りです。

- `line`：`path`、`revision`、`side`、開始行・終了行、コード抜粋を持ちます。単一行なら開始行と終了行は同じです。
- `file`：`path`と`revision`を持ちます。`side`、行番号、`parent_comment_id`は`null`にします。
- `reply`：既存のレビュースレッド内のコメントへの返信に限ります。 `parent_comment_id`を持ちます。親のパス・版が分かれば参照情報として保持し、`side`と行番号は`null`にします。
- 付与先が未確定なら、確定できない値を`null`にし、`location_status: needs_context`とします。分かっているファイルや関数、必要な差分情報はメモに残します。
- 複数の指摘を統合した場合、`source_finding_ids`にすべての元指摘を列挙します。
- 一つの指摘を複数コメントに分けた場合、同じ識別子を保持し、各コメントの中心を別々に記述します。
- `body`以外の作成用メモを、通常のPR本文に混ぜません。

`location_status`は位置を確定できたかを表すものです。本文の事実確認の状態は、`evidence`と`unresolved`で別に扱います。

## 9. 完成前の確認

- [ ] 何を確認・変更したいかが、冒頭から分かる。
- [ ] 問題の成立に必要な入力・環境・操作順を、短縮の際に落としていない。
- [ ] 抽象的な懸念には、具体的な不整合や人が維持している条件が示されている。
- [ ] 疑問形の場合、作成者が何を答えればよいか分かる。
- [ ] 必要な性質と、実現方法の一案を区別している。
- [ ] 付与先は本文の焦点に合い、関連箇所や修正先との関係も分かる。
- [ ] 付与先が、行・ファイルのレビュースレッド、または既存のレビュースレッドへの返信になっている。 PR全体への通常コメントやレビュー本文を付与先にしていない。
- [ ] 行番号・変更前後・対象版を照合し、ファイルコメントを先頭行と混同していない。
- [ ] 提供された規約・仕様以外の要求を、既存の合意として書いていない。
- [ ] 元指摘からの補足に根拠があり、再現や調査の実施を捏造していない。
- [ ] suggestionは選択範囲と対応し、別途必要な変更も分かる。
- [ ] 外部リンク・画像・過去の会話を開かなくても、本文の要点が理解できる。
- [ ] 優先度や担当者などの作成者に不要なメタ情報を、通常の本文から除いている。
- [ ] 条件分岐への指摘では、選択範囲から判定の目的と、条件成立時の処理が読み取れる。条件式だけにした場合は、それだけで十分に理解できる理由がある。
- [ ] 修正案や具体例のうちコードで表現できるものを、自然言語だけで済ませず、必要十分なコード例で示している。
- [ ] 本来の対象範囲にコメントを付けられない場合、本文にその範囲への固定リンクがあり、実際の付与先と指摘対象を混同しない表現になっている。
- [ ] 本文中の参照が「6.8. 関連箇所・規約・画像への参照」を満たしている。
